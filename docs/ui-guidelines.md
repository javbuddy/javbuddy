# UI Guidelines

## Component reuse rule

A UI pattern (markup + logic) used in 2+ places belongs in `Components/Shared/`, not copy-pasted between pages (`AGENTS.md`). "Existing shared components" below reflects what's actually there as of this writing — check it (and re-survey `Components/Shared/` if it looks stale) before adding a new shared component, in case something close already exists.

## Sonarr-Inspired Visual Language

The app is meant to be inspired by Sonarr/Radarr, but there's no design doc or exact snippet to work from — the inspiration lives in what's actually been built. Several commits explicitly did this translation already (`Redesign the movie detail page to match Sonarr's series page`, `Restyle sidebar/header navigation to match Sonarr`, `Add live search-as-you-type to the header, matching Sonarr's dropdown`, `Restyle Library Import to match Sonarr`, `Add Sonarr-style quality and file size on Jellyfin-matched posters`). Treat those as the real reference — when a new page needs "the Sonarr look," match the concrete patterns below (already-established, real translations) before inventing a new one from memory of what Sonarr looks like. If neither this list nor the existing pages answer a specific "how would Sonarr do X" question, say so and ask rather than guess — the same rule `CLAUDE.md` applies everywhere else.

**Status color coding** — a poster's status is a colored accent stripe, not just badge text, mirroring Sonarr's monitored/missing/downloading indicators. Real values from `Components/Shared/PosterCard.razor.css`'s `.poster-image.status-*` classes:

| Displayed as | CSS class | Color |
|---|---|---|
| Missing (a tracked movie's own status — `MovieStatus.Missing`) | `status-wanted` | `#2f8fd6` (blue) |
| Downloading (active torrent, derived at render time — not a `MovieStatus` value) | `status-downloading` | `#e6b800` (yellow) |
| Got (`MovieStatus.Got`) | `status-got` | `#2fa84f` (green) |
| Missing (ActorMissing.razor only — a catalog entry not tracked in your library at all; unrelated to `MovieStatus`) | `status-missing` | `#d9822b` (orange) |

Two unrelated concepts both display as "Missing" with different colors — `MovieStatus.Missing` (a movie you're tracking but don't have) and ActorMissing's own "not in your library" sentinel. Deliberately not confused in code: CSS class selection goes through `MovieStatusExtensions.ToPosterCssClass()`/`ToPosterStatusSuffix()` rather than `MovieStatus.ToString()`, specifically so a tracked-Missing movie keeps the pre-existing `status-wanted` class instead of colliding with `status-missing`. Reuse that extension (or ActorMissing.razor's own `StatusClass` field) for any new "what color is this poster" decision — don't derive a status CSS class from an enum's `ToString()`.

A legend spelling these out in words (`.movies-stats-legend` in `Movies.razor`/`Movies.razor.css`) sits near the stats bar wherever the color coding is used — don't rely on color alone without it, matching the existing pattern.

**Poster wall** — `PosterCard.razor`/`PosterGrid.razor`: a 2:3 aspect-ratio poster image, subtle default shadow (`0 1px 3px rgba(0,0,0,0.15)`) that deepens and lifts 2px on hover, title + secondary metadata line below the image at a smaller font size (`0.8rem` title, `0.7rem` meta, meta colored `#6c757d`) — the standard Sonarr/Radarr poster-grid shape. Reuse `PosterCard`/`PosterGrid` for any new poster-based listing rather than rebuilding this from scratch.

**Sidebar icons** — `NavMenu.razor.css`'s `.nav-icon-*` classes use inline-SVG `mask-image`/`-webkit-mask-image` (Bootstrap Icons paths) with `background-color: currentColor`, not `<img>` tags — this lets the icon inherit the sidebar's text/hover color automatically instead of needing separate light/dark/hover SVG variants. Follow this technique for any new sidebar icon.

**Dark theme** — driven by a `data-theme` attribute on `<html>`, resolved from a cookie by a small inline script in `Components/App.razor` (auto/light/dark, defaulting to `prefers-color-scheme`). Component-level dark overrides live in the same `.razor.css` file as the light styles, scoped with `:root[data-theme="dark"] .some-class { ... }` — see `PosterCard.razor.css`'s dark block (`background: #242833`) for the pattern. Don't put dark-theme rules in a separate global stylesheet; keep them next to the component they style, consistent with CSS isolation (above).

## Blazor CSS isolation gotchas

`.razor.css` files are scoped per component — identical class names in two different `.razor.css` files do **not** share styles. When a new component needs the same look as an existing one, copy the needed CSS rules into the new component's own `.razor.css` rather than assuming reuse across components.

Real example from this codebase: `TorrentSort.razor.css` copies rules it needs from `ActivityQueue.razor`/`MovieDetail.razor`'s own `.razor.css` files rather than referencing them — each page/component keeps its own copy.

## Page vs. component vs. service boundary

Razor pages/components should not inject `IDbContextFactory<AppDbContext>` or an integration client (`IJavinizerClient`, `IJellyfinClient`, etc.) directly for anything beyond a single read-only display query. Data mutation and any non-trivial or cross-cutting query belongs in a service, called from the component (`AGENTS.md`).

Worked example: `ProwlarrSearchModal.razor` injects `IProwlarrClient` and `ITorrentGrabService` directly — acceptable because it's a single-purpose modal performing one focused search-and-grab action, not a page doing broader data orchestration. Compare to `MovieDetail.razor`, which calls into `MovieService`/`SearchService` for its mutations rather than talking to `IDbContextFactory<AppDbContext>` itself.
